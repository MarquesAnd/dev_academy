📦 O segredo do .jar: é um ZIP

O Minecraft inteiro chega ao seu PC como UM arquivo: 1.21.11.jar. E aqui vai a primeira revelação: um .jar é literalmente um .zip com outro nome (Java ARchive). Nós abrimos o da versão 1.21.11 no laboratório — os números REAIS:

MedidaValor real (1.21.11)
Tamanho do arquivo31.152.600 bytes (~29,7 MB)
Arquivos lá dentro28.163
Descomprimido~53 MB (a compressão do zip economiza quase metade)
Classes Java compiladas (.class)10.291 🤯
Pastas na raizMETA-INF, assets, com, data, net

Dez mil classes. Cada uma é um molde como os seus Cachorro e ContaBancaria — só que trabalhando juntas num sistema gigante. E dentro do jar mora um cartão de visitas em JSON, o version.json, que entrega a ficha técnica: "java_version": 21 (o MESMO Java 21 que você vai instalar no Módulo 8!), "protocol_version": 774 (o idioma da rede entre cliente e servidor) e a data de compilação: 09/12/2025.

✱ Por que isso importa
Você acabou de perder o medo do "arquivo de jogo misterioso": é um zip de classes + dados, empacotado exatamente como o SEU projeto Java será um dia. A distância entre você e a Mojang é de escala — não de espécie.

☕ Bytecode: o idioma que a JVM fala

Os 10.291 arquivos .class não são o código-fonte que os devs da Mojang escreveram — são o bytecode: a tradução compilada que a JVM executa. Lembra da viagem do Módulo 1 do Java Completo? App.java → App.class → JVM. O Minecraft é essa viagem, 10 mil vezes.

os primeiros bytes de TODO arquivo .class do planeta
CA FE BA BE  00 00 00 41  ...

Sim: todo .class começa com os bytes "CAFEBABE" em hexadecimal —
a piada de café dos criadores do Java, gravada em bilhões de arquivos
desde 1995. O número seguinte é a versão (0x41 = 65 = Java 21).

E é por a JVM ser a mesma em todo lugar que o MESMO jar roda no Windows, no Mac e no Linux — o "escreva uma vez, rode em qualquer lugar" que você aprendeu, provado pelo jogo mais vendido da história. O manifesto do jar aponta a porta de entrada, e ela tem o nome que você já esperava:

META-INF/MANIFEST.MF (trecho real)
Manifest-Version: 1.0
Main-Class: net.minecraft.client.Main

Ou seja: em algum lugar dessas 10 mil classes existe um public static void main(String[] args) — a MESMA cerimônia do seu primeiro programa. Ao dar dois cliques no jogo, a JVM procura essa classe e chama esse main. O Minecraft começa como o seu "Olá, mundo" começou. ☕

🕵️ Ofuscação: por que as classes têm nomes de espirro

Listando as classes da raiz do jar real, encontramos isto:

nomes reais de arquivos do 1.21.11
gds.class    gds$a.class    gds$b.class    gds$c.class
gdt.class    gdt$1.class    gdt$2.class    fzu$a.class
bjq.class    ← a maior do jar: 245 KB de bytecode numa classe só!

gds?! É a ofuscação: antes de publicar, a Mojang troca os nomes legíveis (imagine ZombieEntity) por códigos curtos — o jar encolhe e engenharia reversa fica mais chata. O $ você decifra com o que sabe: gds$a é uma classe interna (classe dentro de classe), e gdt$1 uma classe anônima — recursos do Java que você verá na estrada.

O plot twist: a própria Mojang PUBLICA oficialmente os "mapas de tradução" (mappings) que revertem a ofuscação — é assim que a comunidade de mods consegue trabalhar. E dentro do jar existe até uma anotação reveladora: net.minecraft.obfuscate.DontObfuscate — a etiqueta que marca o que NÃO pode ser ofuscado (como o Main, que a JVM precisa achar pelo nome!).

💡 Anotações: o @ que você já conhece
DontObfuscate é uma anotação — parente do seu @Override. Anotações são etiquetas que ferramentas leem: uma avisa o compilador ("estou sobrescrevendo"), outra avisa o ofuscador ("não toque aqui"). Mesmo mecanismo, propósitos diferentes.

⏰ O tick: o coração bate 20 vezes por segundo

Lembra do game loop do curso do jogo — 60 voltas por segundo? O Minecraft tem o dele: o tick, e a lógica do mundo roda a 20 ticks por segundo (1 tick = 50 milissegundos). A CADA tick, o servidor faz a mesma dança: mover entidades, crescer plantações, propagar redstone, espalhar fogo, spawnar mobs...

o loop do Minecraft, em espírito
while (servidorLigado) {
    processarTick();      // TODA a lógica do mundo: 1 passo
    esperarAte50ms();     // segura o ritmo: 20 por segundo, cravados
}

Curiosidade que agora faz sentido: os GRÁFICOS rodam a 60+ fps, mas a LÓGICA a 20 tps — dois relógios separados. Por isso um "clock de redstone mais rápido possível" pisca 10x por segundo (precisa de 2 ticks por ciclo): é o tick, não o fps, que manda no mundo.

🐌 O orçamento de 50ms: de onde vem o LAG

Se a lógica roda a 20 tps, cada tick tem um ORÇAMENTO: 50 milissegundos para processar o mundo INTEIRO. E se não der tempo?

SituaçãoO que aconteceComo o jogador sente
Tick gasta 30msSobram 20ms; o servidor descansaMundo fluido, 20 tps
Tick gasta 80msO próximo atrasa — TPS cai para ~12"Servidor lagado": mobs teleportando, blocos que voltam
Fazenda com 5.000 entidadesMilhares de updates por tick estouram o orçamentoO famoso lag das farms gigantes 😅

Por isso existem limites de mobs por área, itens agrupados no chão viram UM objeto, e chunks longe de jogadores nem processam. Tudo é engenharia de orçamento: performance é caber no tempo do tick.

💡 Isso é profissão
Troque "tick de 50ms" por "requisição de API que deve responder em 200ms" e você tem o dia a dia de backend. Orçamento de tempo, medir o que consome, otimizar o gargalo — o Minecraft ensina performance melhor que muito curso.

Todo zumbi, vaca, flecha e vagoneta do Minecraft é um OBJETO — e a hierarquia de herança (documentada pela comunidade via mappings oficiais) é um manual de OO em produção:

a árvore (simplificada) — cada seta é um extends
Entity                     ← TUDO que existe no mundo: posição, movimento, tick()
 ├─ LivingEntity           ← o que tem VIDA: HP, dano, morte, efeitos
 │   ├─ Player             ← você! (vida + inventário + experiência)
 │   ├─ Mob                ← o que tem IA própria
 │   │   ├─ Zombie, Skeleton, Creeper...
 │   │   └─ Animal → Cow, Pig, Wolf...
 ├─ ItemEntity             ← item caído no chão (tem posição, NÃO tem HP)
 └─ ArrowEntity, Boat...

(toque num nó — experimente o Creeper e a Cow)

🎭 O loop mais polimórfico do planeta

Junte os módulos 2 e 3 e você enxerga o coração do jogo: a cada tick, o servidor percorre a lista de entidades do mundo e chama o MESMO método em cada uma — e cada uma responde do seu jeito:

o espírito do código do servidor
for (Entity e : entidadesDoMundo) {
    e.tick();     // zumbi persegue · vaca pasta · flecha voa · item gira
}

UMA linha de chamada; MIL comportamentos. O zumbi sobrescreveu tick() para caçar você; a vaca, para pastar; o creeper, para... você sabe. É o coral da fazenda do Java Completo — rodando 20 vezes por segundo num mundo com milhares de seres. Polimorfismo não é teoria de prova: é o que faz o Minecraft ser vivo.

✱ Feche os olhos e veja

Aperte F3 no jogo e olhe: sua posição tem vírgula (XYZ: 127.534 / 64.000 / -213.871), mas o bloco onde você pisa não (Block: 127 64 -214). Não é acaso — são os tipos do Java:

O quêTipoPor quê
Entidades (você, mobs, flechas)double x, y, zMovimento suave exige frações — andar é somar 0.21 por tick
Blocosint x, y, zBloco é grade: existe o bloco 127, não o bloco 127.5
Altura do mundoy de -64 a 320384 camadas (desde a atualização das cavernas)

E a conversão entre os dois mundos é o velho conhecido: arredondar para baixo. Você em x = -0.5 está no bloco... -1! (floor, não truncar — o detalhe que derruba muito dev, e que o próximo lab esclarece de vez.)

🏔️ De números a montanhas: o ruído

Seed → números "aleatórios" → ...montanhas? O elo perdido chama-se ruído coerente (Perlin/Simplex): em vez de sortear a altura de cada bloco solto (viraria estática de TV), a função de ruído gera valores SUAVES — vizinhos parecidos, transições graduais:

a ideia, em uma linha de espírito
altura(x, z) = ruido(seed, x, z)   // vizinho de montanha é montanha; de vale, vale

Empilhe camadas: ruído grande = continentes · médio = colinas · fino = pedrinhas.
Some tudo => terreno. Outro ruído decide biomas; outro, cavernas...

É geração procedural: o mundo não está salvo em lugar nenhum — é CALCULADO da seed quando você chega perto (por chunk!). Bilhões de mundos possíveis, zero artistas desenhando mapas. Matemática fazendo o trabalho de um exército.

💡 Junte as peças do módulo
Seed (determinismo) + chunks (pedaços sob demanda) + ruído (suavidade) = mundos infinitos, idênticos para quem tem a mesma seed, gerados só onde importa. Três conceitos simples, um resultado lendário.

📣 O padrão observer: o mundo que avisa

Quebrou um bloco. Quem precisa saber? A estatística conta +1, o avanço confere se era diamante, a ferramenta gasta durabilidade, a fazenda automática reage... Se o código do bloco tivesse que CONHECER todo mundo, seria um espaguete infinito. A solução da engenharia: eventos.

o padrão observer (a ideia inteira)
1. Interessados se INSCREVEM:   "me avise quando quebrarem blocos"
2. O evento ACONTECE:           jogador quebra um diamante
3. O mundo NOTIFICA a lista:    for (Ouvinte o : inscritos) { o.aoQuebrarBloco(...); }
4. Cada um reage do seu jeito — sem que o bloco conheça NINGUÉM

Você já viveu isso duas vezes: o onclick do HTML (o navegador notifica o clique) e os aoPegarMoeda do seu jogo (a engine notifica o toque). O Minecraft é uma sinfonia de eventos — e é NELES que os plugins se penduram, como você fará no Módulo 8.

EventoQuebra ev = new EventoQuebra(jogador, bloco);

🔴 Redstone: o boolean que virou bloco

A redstone é o Módulo 2 do Java Completo construído com pedras: sinal de 0 a 15 (que para a lógica vira ligado/desligado — um boolean), fios que o carregam, e componentes que o transformam:

No jogoNa lógica
Alavanca / botão / placa de pressãoA ENTRADA: true ou false
Poeira de redstoneO fio: leva o sinal (perdendo 1 de força por bloco — por isso o máximo 15!)
Tocha de redstone num bloco alimentadoNOT: inverte! Alimentou → apaga; sem sinal → acende
Pistão / lâmpada / portaA SAÍDA: o efeito do true

E aqui a beleza: a tocha (NOT) é a peça-mãe. Com NOTs combinados se constrói QUALQUER porta lógica — e com portas lógicas se constrói... um computador. Não é força de expressão: já construíram computadores funcionais dentro do Minecraft, de calculadoras a processadores. Booleana até o fim.

🔌 SEU primeiro plugin, linha a linha

O rito de passagem. Um plugin Paper é uma classe que estende JavaPlugin + um listener de eventos — TUDO conceitos seus. O código completo (este é SEU código, usando a API pública — pode publicar!):

MeuPlugin.java — boas-vindas + comando /ola
public class MeuPlugin extends JavaPlugin implements Listener {

    @Override
    public void onEnable() {                          // o "construtor" do plugin: roda ao ligar
        getServer().getPluginManager().registerEvents(this, this);
        getLogger().info("MeuPlugin ligado! ✱");      // aparece no console do servidor
    }

    @EventHandler                                     // "me inscreva neste evento" (Módulo 6!)
    public void aoEntrar(PlayerJoinEvent evento) {
        Player p = evento.getPlayer();                // o objeto Player (Módulo 3!)
        p.sendMessage("§aBem-vindo(a) ao meu mundo, " + p.getName() + "!");
        evento.setJoinMessage("§e✱ " + p.getName() + " chegou para construir!");
    }

    @Override
    public boolean onCommand(CommandSender quem, Command cmd, String rotulo, String[] args) {
        if (rotulo.equalsIgnoreCase("ola")) {        // equals, não == (você sabe por quê 😉)
            quem.sendMessage("§bOlá! Plugin feito por um(a) formando(a) da Dev Academy.");
            return true;
        }
        return false;
    }
}

Empacote (o IntelliJ gera o .jar do plugin — um jar SEU, com manifesto e tudo), solte na pasta plugins/ do servidor, reinicie. Entre no jogo e digite /ola. Aquela mensagem azul na tela? Seu Java rodando DENTRO do Minecraft.

✱ O inventário de conceitos deste código
extends e implements (M7 do Java), @Override e anotações (M1 daqui!), eventos e inscrição (M6), o objeto Player da hierarquia Entity (M3), equalsIgnoreCase (M8 do Java), o jar com manifesto (M1). Não sobrou UMA linha misteriosa. Este é o teste final de verdade — e você passou lendo.
