🤖 O que é programar, afinal?

Programar é escrever instruções para uma máquina obedecer. Só isso. O detalhe importante: o computador é absurdamente rápido e absurdamente literal. Ele não interpreta, não deduz, não "entende o que você quis dizer". Ele faz exatamente o que está escrito.

✱
Pensa num estagiário genial, que trabalha na velocidade da luz, nunca cansa... mas que segue a receita ao pé da letra. Se a receita estiver vaga, o bolo sai errado. Se estiver perfeita, ele faz 1 milhão de bolos por segundo.

Módulo 1 · Lição 4 de 4

🏠 Onde o CORTEX mora: frontend e backend

Duas palavras que você vai ouvir para sempre:

🪟 FRONTEND (a recepção)
Tudo que roda no navegador do usuário: as telas, botões, gráficos. No CORTEX, são os arquivos HTML, CSS e JS guardados no repositório GitHub Pages. Qualquer pessoa que visita o site "baixa" uma cópia deles.
🔐 BACKEND (a sala do arquivo)
Tudo que roda no servidor, longe dos olhos: o banco de dados, as regras de acesso, os gatilhos automáticos. No CORTEX, é o Supabase — um PostgreSQL com porteiro na porta.

E como o frontend sabe onde fica o backend? Por um arquivinho chamado config.js, que guarda o endereço do Supabase e uma chave de visitante. É o crachá que a recepção usa para pedir fichas na sala do arquivo.

⚠️ Momento segurança
A chave que fica no frontend é a chave "pública" (anon). Ela só abre o que as regras do banco permitem — por isso as políticas de acesso (RLS) no Supabase são tão importantes. Chave poderosa nunca vai no frontend, porque todo visitante consegue ler os arquivos do site.

🧱 Tags: os blocos de LEGO da web

HTML é feito de tags. Uma tag é um bloco com nome, escrito entre < e >. Quase toda tag vem em par: uma que abre e uma que fecha (a de fechar tem uma barra /).

anatomia de uma tag
<p>          ← abre o "parágrafo"
Olá, mundo!   ← o conteúdo
</p>         ← fecha (repare na barra /)

As tags que você mais vai ver no CORTEX:

TagO que éNa clínica seria...
<h1>...</h1>Título grande (h2, h3... vão diminuindo)🪧 A placa da fachada
<p>...</p>Parágrafo de texto📄 Um texto no mural
<button>...</button>Botão clicável🔔 A campainha do balcão
<input>Campo para digitar (não fecha!)✍️ Linha em branco do formulário
<div>...</div>Caixa invisível para agrupar coisas📦 Uma bandeja que organiza itens
<img>Imagem (também não fecha)🖼️ Quadro na parede
✱
Umas poucas tags são "autocolantes" e não fecham: <input>, <img>, <br>. O resto, se abriu, tem que fechar — esquecer de fechar uma <div> é uma das causas nº 1 de tela bagunçada!

🏷️ Atributos: etiquetas coladas nas tags

Uma tag pode carregar informações extras chamadas atributos. Eles ficam dentro da tag de abertura, no formato nome="valor".

exemplo real (simplificado) do CORTEX
<button class="btn-salvar" id="botaoLaudo" onclick="gerarLaudo()">
  Gerar Laudo PDF
</button>

Os três atributos que resolvem 90% da vida:

  • class 👕 — o uniforme. Vários elementos podem vestir a mesma class, e o CSS estiliza todos de uma vez. Ex.: todos os cards de paciente usam class="card-paciente".
  • id 🪪 — o CPF. Identidade única, só UM elemento pode ter cada id. O JavaScript usa o id para encontrar exatamente aquele elemento.
  • onclick 👆 — a campainha ligada no cérebro: "quando clicarem aqui, chame tal função do JavaScript".
💡 Manutenção na prática
Quando você pede "mude o botão X", eu procuro pelo id ou pela class dele no arquivo. É o GPS do código. Por isso nomes claros importam: botaoLaudo conta uma história; btn3 não conta nada.

📦 Todo elemento é uma caixa (e você controla os respiros)

Pense num quadro pendurado na parede: o quadro tem a arte, o passe-partout (espaço interno), a moldura, e uma distância dos outros quadros. No CSS:

  • padding = passe-partout → espaço dentro, entre a borda e o conteúdo
  • border = a moldura
  • margin = distância fora, até os vizinhos
  • border-radius = o quanto os cantos são arredondados

Padding deixa o card "gordinho" por dentro. Margin afasta um card do outro. Quando você me pede "dá um respiro entre os cards", em código isso vira margin. "O texto tá colado na borda" vira padding. Agora você fala a língua!

🌈 Cores hex e os degradês do CORTEX

Cores no CSS geralmente aparecem em código hexadecimal: uma cerquilha + 6 caracteres, tipo #2F6FED. São 3 pares: vermelho, verde e azul (RR GG BB), de 00 (nada) a FF (máximo). #000000 = preto, #FFFFFF = branco.

🎨 A paleta oficial do CORTEX — toque numa cor para pintar o card:

navy
azul
roxo
âmbar
verde
✱ CORTEX · Painel da Clínica
background: linear-gradient(135deg, #2F6FED, #7C4DFF);

O linear-gradient é a assinatura visual do CORTEX: linear-gradient(ângulo, cor1, cor2) cria uma transição suave entre duas cores. 135deg = diagonal ↘.

📎 Curiosidade de guerra
Nem tudo aceita degradê: quando o CORTEX "fotografa" a tela para gerar PDF (html2canvas), degradês radiais não saem na foto — por isso alguns fundos de laudo usam imagem de textura. Programar também é conhecer as manias das ferramentas!

🎁 Variáveis: caixinhas com etiqueta

Uma variável é uma caixinha na memória com uma etiqueta (o nome) e um conteúdo (o valor). Criamos com let (pode trocar o conteúdo) ou const (lacrada — não troca mais).

🧠 caixinhas
let nomePaciente = "João Silva";  // texto (sempre entre aspas)
let idade = 34;                   // número (sem aspas!)
const CLINICA = "Equilibrium";   // lacrada: nunca muda

idade = idade + 1;  // aniversário! a caixinha agora guarda 35
⚠️ Pegadinha clássica
"34" com aspas é TEXTO; 34 sem aspas é NÚMERO. Texto + texto gruda: "34" + "1" vira "341" 😱. Número + número soma: 34 + 1 = 35. Metade dos bugs de iniciante mora aqui.

🚦 if / else: o código toma decisões

SE (if) uma condição for verdadeira, faça isto; SENÃO (else), faça aquilo. É a recepcionista triando: SE idade ≥ 18 → protocolo adulto; SENÃO → protocolo infantojuvenil. O CORTEX faz exatamente isso ao escolher qual versão de instrumento aplicar!

🧠 triagem em código
if (idade >= 18) {
  aplicarBateria("RAADS-R");      // versão adulto
} else if (idade >= 12) {
  aplicarBateria("AQ-Adolescente"); // 12 a 17
} else {
  aplicarBateria("ASSQ");           // crianças
}

Sem WHERE, o arquivista traz a gaveta INTEIRA. Com WHERE, você filtra: SELECT * FROM pacientes WHERE condição.

  • Textos vão entre aspas simples: cidade = 'Araguari'
🗄️ SIMULADOR SQL · gaveta: pacientes

🎯 Missões: 1️⃣ Encontre só os pacientes de Uberlândia. 2️⃣ Encontre quem tem menos de 18 anos (olha o if/else da recepcionista de novo!). 3️⃣ Busque a ficha exata do id 5.

Módulo 5 · Lição 5 de 6

✏️ UPDATE: corrigindo fichas (primeira zona de perigo)

Alterar = UPDATE gaveta SET campo = valor WHERE quem. E aqui mora o perigo mais famoso do SQL:

🚨 A regra que salva carreiras
UPDATE sem WHERE altera TODAS as fichas da gaveta. Todas. De uma vez. O banco não pergunta "tem certeza?" — ele obedece (lembra do robô literal da Lição 1?). No CORTEX, um UPDATE sem WHERE em aplicacoes_instrumento mudaria o status de MILHARES de testes num piscar.
🗄️ SIMULADOR SQL · pode errar aqui, é pra isso que existe 😈
cirúrgico: só o id 3 conferir 😈 SEM WHERE (faça e veja!)
🎯 Missão de coragem: rode o UPDATE cirúrgico e confira. Depois rode o 😈 sem WHERE, veja a tragédia com os próprios olhos... e salve o dia com o botão Restaurar backup. Sentiu o poder do backup? Essa sensação é a lição.
💡 É assim no CORTEX real
Quando um teste é corrigido, roda a essência de: UPDATE aplicacoes_instrumento SET status = 'corrigido' WHERE id = 123. Uma ficha, um id, uma mudança. Cirurgia, não bombardeio.
🎉 Sobreviveu à zona de perigo!

🗑️ DELETE + o protocolo de segurança do CORTEX

DELETE FROM gaveta WHERE quem — passa a ficha no triturador. Não tem lixeira, não tem Ctrl+Z. Por isso, no CORTEX seguimos um protocolo cirúrgico antes de qualquer operação destrutiva:

🏅 O Protocolo (nascido de batalhas reais)
1. SELECT antes. Rode um SELECT com o MESMO WHERE e olhe nos olhos das fichas que vão morrer. É a biópsia antes da cirurgia.
2. WHERE por id exato. Nome pode repetir; id não.
3. BEGIN → conferir → COMMIT. O "modo rascunho" do banco: BEGIN abre um ensaio, você executa e confere, e só o COMMIT torna real (ROLLBACK desfaz tudo).
4. Backup respirando. Antes de mexer grande, garanta o ponto de restauração.
o protocolo em código
-- 1) biópsia: quem exatamente vai ser apagado?
SELECT * FROM pacientes WHERE id = 7;

BEGIN;                                -- 2) abre o modo rascunho
DELETE FROM pacientes WHERE id = 7;  -- 3) a cirurgia
SELECT * FROM pacientes;              -- 4) conferiu? tudo certo?
COMMIT;                               -- 5) agora sim, é definitivo
🗄️ SIMULADOR SQL · último treino
1º a biópsia 2º o DELETE certeiro 💀 DELETE sem WHERE

🧩 Bônus: 3 palavras que você já ouviu no CORTEX

  • Trigger 🔔 — alarme automático do banco: "QUANDO acontecer X numa tabela, execute Y sozinho". É assim que corrigir um teste consome 1 licença do estoque sem ninguém pedir.
  • RPC 📋 — um procedimento pronto no balcão: em vez de o frontend mandar 5 comandos, ele chama UMA função do banco (ex.: publico_finalizar_aplicacao) que faz a sequência inteira com segurança.
  • View 🪟 — uma "gaveta virtual": um SELECT salvo com nome, que se comporta como tabela (ex.: vw_pacientes_lista, que já entrega os dados prontinhos pra tela).

🗃️ Objetos: a ficha completa

Um array de nomes é pouco: paciente tem nome, idade, cidade... Para agrupar informações de UMA coisa, existe o objeto — a ficha com campos nomeados, entre chaves:

let pacientes = [

🔎 filter & find: a busca instantânea

📊 ORDER BY & LIMIT: ordem na fila

O arquivista entrega as fichas na ordem que quiser — a menos que você mande ordenar. ORDER BY ordena, LIMIT corta a fila:

ordenando e cortando
SELECT * FROM pacientes ORDER BY idade DESC;   -- DESC = maior→menor; ASC (padrão) = menor→maior
SELECT * FROM pacientes ORDER BY nome LIMIT 3; -- alfabética, só os 3 primeiros

⚠️ Detalhe de gente literal: as cláusulas têm ordem fixa de escrita — WHERE, depois ORDER BY, depois LIMIT. Trocar a ordem = o arquivista devolve erro.

🛂 RLS: o crachá que mora DENTRO do banco

Hora de revelar o segredo de segurança mais importante do CORTEX — e desta escola. RLS (Row Level Security) = regras de acesso linha por linha, escritas no próprio banco. Você já RODOU uma, na instalação da Academy:

anatomia de uma policy (a que protege SEU progresso)
create policy "ler o proprio progresso"
  on public.progresso_cursos for select
  using ( auth.uid() = user_id );

Tradução, palavra por palavra: "Nesta tabela, um SELECT só devolve as linhas onde o id de quem está logado (auth.uid()) for igual ao user_id da linha." Ou seja: cada um enxerga só o que é seu — mesmo que tente pedir tudo.

Nas policies de escrita entra o with check: "só aceito gravar se a linha nova também for sua". using filtra o que sai; with check filtra o que entra.

✱ Agora faz sentido a anon key pública
É por ISSO que a chave anon pode ficar no código sem medo: ela só abre a porta da frente. Quem decide o que cada pessoa vê é a RLS, lá dentro, linha por linha. Porta pública, cofres individuais.
🚨 Cicatriz real: a view espiã
Uma view do CORTEX (vw_pacientes_lista) rodava como SECURITY DEFINER — "com o crachá do dono" — e por isso ignorava a RLS de quem consultava. Correção: security_invoker = true ("use o crachá de quem pergunta"). Lição: view também precisa respeitar o porteiro. Esse tipo de detalhe é segurança de dados clínicos de verdade.
🎉 Lição concluída!
